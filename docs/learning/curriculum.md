# 学习路线：规则与流程（公开部分）

> 2026-10-27 建立。路线的终点公开，路线本身（每个 ticket 之后会遇到什么）保存在仓库之外的隐藏计划里，只有 Claude 读。
> 本文件说明"怎么走"，不说明"会遇到什么"。

## 1. 目的

1. 真正学会编程和数据工程：代码自己写，数据问题自己发现、自己修。
2. 完成 FYP 1、FYP 2 报告，每个设计决定都有文献和数据两种依据。
3. 能向面试官讲清楚项目的每一部分，以及它是怎样一步步做出来的。

## 2. 终点

终点是当前设计基线：[`docs/fyp-design/fyp_project_design_v0.5.md`](../fyp-design/fyp_project_design_v0.5.md)。

- 每个阶段的出口标准直接取自设计书的里程碑（§10.5），所以路线一定走到这个终点。
- 文献综述可能改变终点（见第 9 节）。终点的任何改动都会公开告诉你。

## 5. 一个模块的循环

1. **研究**（需要时）：读 Claude 写的文献导读，回答问题。
2. **ticket v1**：Claude 发出 ticket。ticket 只会少写，不会写错，也不会禁止正确做法。
3. **预测 → 运行 → 检查**：动手前在 PR 描述里写下预测；运行 ticket 里的检查；把预测和实际结果对比。
4. **遇到问题**：先写症状记录，需要时再要提示（第 6 节）。
5. **讲解**：问题解决后，Claude 讲原因、概念名称、行业做法、对应设计书哪一节，再问一道迁移题（"管道里还有哪里会出现同一类问题？"）。
6. **ticket v2**：下一步。
7. **收尾**：回答复盘四问（第 8 节）→ Claude 写工程日志 → 你读一遍 → 合并 PR。

不是每个 ticket 都会遇到问题。没遇到也不代表做错了，可能是你一开始就做对了。

## 6. 提示规则

**遇到问题时，先写症状记录**（发在聊天里，中文几句话即可）：
- 预期是什么？
- 实际看到了什么？（哪个检查、什么数字）
- 已经试过什么？

**提示分四级，你开口才给：**

| 级别 | 内容 |
|---|---|
| L1 | 往哪里看 |
| L2 | 该算什么、该跑什么检查 |
| L3 | 概念的名称 |
| L4 | 完整解释和修正方向（代码仍然由你写） |

- 同一个症状有效投入约 90 分钟（或跨了两次 session）还没有进展，Claude 会问你要不要下一级，你可以拒绝。
- review 时如果某个检查结果和你的预测不一致而你没有注意到，Claude 只会指出"哪个检查和预测不一致"，不说原因。
- 每次用到的提示级别都会记下来。随着时间推进，用到的提示越来越少，这本身就是成长的证据。

## 7. 预测与检查

- 每个有运行结果的 ticket 都有"运行前预测"。先写预测再运行，不要事后改。
- 检查是通用的数据工程习惯：行数、唯一性、取值范围、分布、对账（"这里的数量应该等于那里的数量"）。检查结果贴进 PR。
- 每张表都要回答"一行代表什么"，并且验证它。

## 8. 复盘四问（每次问题解决后、PR 合并前）

用中文回答，几句话即可：
1. 你原本预期什么？
2. 实际看到了什么？（哪个检查、什么数字）
3. 你是怎么找到原因的？
4. v2 改了什么？为什么这样改有效？

Claude 根据你的回答、commit、PR 和检查输出写英文工程日志，你读一遍，有不对的地方告诉 Claude。这四个问题就是面试官会问的问题。

## 9. 文献与设计变化

- 文献关口：**G1**（约 12-20，Proposal Ch2 完成后）、**G2**（约 03-07，FYP1 文献扩写后）、**G3**（06-30）。
- 文献推翻原计划时：
  - 还没开工的部分：直接改，写 ADR，设计书升版本；
  - 已经做了的部分：新方法作为 RQ 里的对比组，或者写进局限与 Future Work。
- 终点的改动会公开告诉你。

## 11. 记录与展示

| 记录 | 位置 | 语言 | 谁写 | 给谁看 |
|---|---|---|---|---|
| ticket | [`docs/tickets/`](../tickets/README.md) | 中文 | Claude | 你（学习材料，提交学校前排除） |
| PR | GitHub | 英文 | 你开 PR，Claude review | 导师、面试官 |
| 工程日志 | [`docs/engineering-log/`](../engineering-log/README.md) | 英文 | Claude（根据复盘四问），你审阅 | 导师、面试官、FYP1 Ch4、FYP2 Ch5.5 与 Ch6.3 |
| ADR（设计决定记录） | [`docs/adr/`](../adr/README.md) | 英文 | Claude，你读懂 | 报告 Ch3/Ch4、面试 |
| 教学手册 | `docs/learning/` | 中文 | Claude（每阶段结束） | 你的复习与面试准备 |

- **早期代码**：最终的代码树里不保留 v1 文件。v1 留在 git 历史里，日志里有 commit 链接；每个阶段结束打一个 tag。作为实验对比组的版本（例如 RQ1 的两种方法、RQ2 的规则开关）以配置选项的形式保留。
- **发现日期要诚实**：数据源的很多问题在 2026-10 的桌面调研中已经由 AI 辅助登记（git 历史可查）。工程日志里分开写"10 月已登记"与"实现时由哪个检查发现、量化成多少"；真正的新发现单独标出。

## 12. 分支与 PR

每个 ticket 一个分支，PR 合并时选 **Create a merge commit**（保留每个 commit，v1 到 v2 的过程才看得到）。具体命令见 [`docs/tickets/README.md`](../tickets/README.md)。

## 13. 抽查

每两周一次，15–20 分钟，不看笔记。题目来自已完成的模块、已解决问题的迁移题，以及"设计书为什么要有 X"。答不上的题下次再考。

## 14. 会话约定

- 你说"开工"或者直接说要做哪个 ticket：Claude 先读进度。
- 你说"收工"：Claude 更新进度，聊天里只说"已更新进度"。
- 思考档位：阶段交界、关口、重排、设计书新版本、报告结构用 xhigh；发 ticket、review、提示、讲解用 high；库用法小问题用 medium。
