## 我是谁，我想要什么

我是一名最后一年的学生，在做数据工程方向的 FYP。我的最终目的有三个：

1. 真正学会编程和数据工程：做完以后能自己手写代码、自己发现和解决数据问题，而不是只会 vibe coding。vibe coding 做得更多更快，但我学不到东西。
2. 完成学校的 FYP 报告（FYP1、FYP2），报告里的设计决定需要有文献综述（lit review）支持。
3. 毕业找工作时，能向面试官讲清楚项目中每一个部分，以及我是怎么一步步做出来的。

## 目前的状态

- 项目方向、数据源、架构设计都是 AI 主导完成的：AI 总结了数据源（包括坑点、脏点），又基于总结设计了架构。当前设计基线是 v0.4。
- collector VM、ingestion、bronze_sync、CI 等基础部分已经由 AI 写好。
- 现行工作模式（见 `CLAUDE.md`）：我写核心代码，AI 当 tech lead 写 ticket、给提示、review。
- 我在 `practice` 分支做了一个练习 ticket（`practice/tickets/T01-weather-downloader.md`，只在 practice 分支上，用 `git show practice:<path>` 读）。
- 我读过 AI 写的数据源总结，但只记得大概，具体坑点不记得。

## 我的想法（请先判断它是否合理）

我发现一个问题：AI 从一开始就按高标准设计了架构和代码，所以项目里没有"从基本达标的代码到符合设计约束的代码"这个过程。数据源分析也一样：坑点是 AI 直接写出来的，没有"我写代码 → 发现脏数据 → 记录下来"的过程。导师或面试官问"你什么时候发现这个问题的？你写了什么、做了什么才发现的？"，我答不出来。完整跑通的项目里看不到这个过程，而这个过程恰恰是我应该学的。

所以我的想法是：

- AI 事先知道一切（数据源、数据源的坑、架构怎么设计）。但它给我的任务故意不包含这些信息，让我撞墙。
- 比如它知道这里会数据倾斜，却故意让我写解决不了这个问题的代码。我写完运行发现有问题，它不主动说；等我主动问，它才解释这是什么，然后把它早就计划好的下一步任务交给我。
- 重点是这个过程最终会做出我们最初同意的架构，而不是随机的。我知情的是最初定好的终点，过程中的安排我不知情。
- 每一版代码做不到什么、下一版做到了什么，都要记录下来，作为我真正学到了什么的证据，让 FYP 导师和面试官看到。

**请你先独立判断：**
- 这个想法能不能达到我上面的三个最终目的？有没有更好的方法？
- 有什么风险或盲点（时间、学习效率、和学校报告要求的冲突、AI 跨会话没有记忆等）？
- 如果你认为应该调整，直接提出你的方案，不要因为这是我的想法就照做。

## 你必须考虑的几个不确定性

1. **文献综述会改变设计**。学校要求设计决定有 lit review 支持，所以你不可能事先知道一切：你现在定了方案 A，lit review 可能支持方案 B。计划需要把这种未知考虑进去（比如在什么阶段做 lit review、哪些决定要等 lit review 之后才定、lit review 推翻原计划时怎么调整）。先看 `reports/proposal/` 里已经写了什么。
2. **设计基线可以演进**。终点不一定是 v0.4 原封不动。如果你判断有必要（因为 lit review、时间、可行性或教学需要），可以提出 v0.5，但要写明改了什么、为什么改，而且总体上要和最初的设计大致相同。
3. **时间有限**。根据学术日历判断时间够不够，据此决定做多少、砍什么。
4. **数据源的坑需要我重新亲手找一遍**。我不记得具体坑点。AI 之前找过的结果可以当作"答案"，但发现过程需要我自己走一遍。

## 需要你自己做决定的问题

- 已经由 AI 写好的 ingestion 代码不要改。要不要让我另外把 ingestion 的关键部分重新走一遍，由你根据时间判断。
- 过程怎么记录和对外展示：我听说过 GitHub Issues + PR、ticket（据说大公司的 ticket 比 Issues 更详细）、ADR、devlog 等做法。我只是提意见，没有偏好要你照做。请评估后自己决定用什么、放在哪里，以及最终 repo 里是否保留早期版本的代码。
- 哪些墙值得让我撞、哪些不值得（比如环境配置这类只耗时间、学不到核心能力的问题）。
- 隐藏的计划放在哪里、怎么保证跨会话延续（AI 没有跨会话记忆，必须写进文件；我承诺不打开隐藏的部分）。
- 计划的具体结构、ticket 的格式和粒度、思考档位如何分配（这次用 xhigh，日常推进我打算用 high）。

## 工作方式：分两阶段

**第一阶段（这一轮）：只讨论，不创建文件。**
先读资料，然后在聊天里告诉我：
- 你对这个想法是否合理的判断，以及你建议的整体方法；
- 上面"需要你自己做决定的问题"的结论和理由；
- 时间安排的大致轮廓；
- 你要创建或修改哪些文件。

注意：第一阶段的回答**不能透露任何具体的陷阱或数据源坑点**，只讲方法和结构。然后等我确认。

**第二阶段（我确认后）：落成文件。**
按讨论结果创建隐藏计划、公开部分和跨会话规则（例如更新 `CLAUDE.md`，但写进去的只能是规则，不能有具体陷阱）。完成后在聊天里只列出文件清单，不透露陷阱。
